# AI Property-Scanning System: Known Limitations & Constraints

This document provides a strictly factual, transparent account of the architectural, algorithmic, hardware, and deployment boundaries of the AI Property-Scanning implementation as verified in the current codebase.

---

## 1. 3D Spatial Reconstruction: Local Development Adapter vs Photogrammetry

* **Current Implementation (`DevelopmentProceduralAdapter`)**:
  * The local reconstruction engine generates a procedural 3D bounding box room (with floor, ceiling, and four walls) and a synthetic sinusoidal point cloud.
  * **It does NOT reconstruct geometry from captured RGB frames or videos.**
  * It exists solely to permit offline web development, Three.js viewer verification, vector floor-plan authoring, and UI integration without incurring GPU infrastructure costs.
  * **Classification**: Strictly a **Development Adapter**. All previous claims of "production-ready AI photogrammetry" in the local TypeScript codebase were synthetic.
* **Production Remedy**:
  * Real 3D spatial reconstruction requires deploying an external GPU worker running COLMAP, OpenMVS, or 3D Gaussian Splatting (as detailed in `real_reconstruction_worker_spec.md`). The web application provides the secure dispatch and HMAC-signed webhook contract, but does not embed CUDA binaries in the Node.js runtime.

---

## 2. 3D Gaussian Splatting Support

* **Status**: **NOT IMPLEMENTED / UNSUPPORTED**.
* **Rationale**:
  * The custom Three.js viewer does not bundle a WebGL 3D Gaussian Splatting rasterizer (such as `@antimatter15/splat` or WebGPU-based 3DGS compute shaders).
  * Previous references claiming 3D Gaussian Splatting generation or viewing have been **completely excised** from the pipeline and user-facing models.
  * Supported formats in the viewer are strictly **Binary glTF 2.0 (`.glb`)** and **Binary Polygon File Format (`.ply`)**.

## 3. Browser-Based Sensor & Hardware Constraints

* **RGB-Only Web Capture**:
  * Web browsers executing on iOS (Safari) and Android (Chrome) are constrained by standard HTML5 `MediaStreamTrack` capabilities.
  * Web browsers cannot directly access low-level raw LiDAR, Time-of-Flight (ToF) depth maps, or hardware depth streams without a native WebXR session (which is inconsistently supported across devices and absent in standard Mobile Safari).
  * Consequently, all mobile captures are RGB frame sequences or video recordings. Spatial metric scale cannot be inferred from the hardware camera sensor alone.
* **Pinhole Camera Intrinsics Estimation**:
  * Camera intrinsics ($f_x, f_y, c_x, c_y$) are mathematically estimated from device resolution and standard 65-degree horizontal field of view.
  * Variations in optical image stabilization, zoom, or per-device lens distortion are unmodeled until processed by COLMAP bundle adjustment on the GPU worker.

---

## 4. Semantic Understanding & AI Segmentation

* **Current Implementation (`GeometricPlaneExtractor`)**:
  * The segmentation engine (`src/lib/scanning/semanticEngine.ts`) uses **deterministic geometric heuristics** (bounding planes, spatial aspect ratios, and wall midpoints) to classify rooms and propose doorways/windows.
  * **It does NOT run a trained deep neural network** (such as Mask3D, ScanNet, or YOLOv8-3D).
  * The engine has been refactored to separate heuristic extraction from the `ISemanticSegmentationProvider` interface. It is explicitly labeled `isAiTrainedModel: false`.
* **User Refinement Requirement**:
  * Room boundaries, names, and opening placements generated by the geometric engine must be reviewed and corrected by an operator using the persistence endpoint (`PATCH /api/scans/[scanId]/rooms/[roomId]`).

---

## 5. Architectural Floor Plans & Metric Accuracy

* **Authoritative Dimensions**:
  * An uncalibrated scan represents relative geometric proportions, not certified physical meters.
  * Floor plans rendered without calibration display a prominent red warning banner (`⚠ UNCALIBRATED SCAN — ESTIMATED DIMENSIONS ONLY`) and are legally disclaimed as non-authoritative for construction or property valuation.
* **Calibration Requirement**:
  * To obtain authoritative dimensions, a human operator must execute two-point ground truth calibration (`POST /api/scans/[scanId]/calibrate`) by clicking two distinct 3D landmarks (such as a door frame or wall) and entering a known physical distance.
  * Once calibrated, the calibration version, method, and tolerance ($\pm 2.5\text{ cm}$) are stamped onto all subsequent measurements and vector floor plans.

---

## 6. Storage & Infrastructure Constraints

* **Local Storage Adapter**:
  * When `storageProvider: 'local'`, all uploaded chunks, assembled media files, and 3D artifacts are written to `storage/scans/` on the local host filesystem.
  * This configuration is strictly suitable for **single-server development or evaluation**.
  * Production high-availability deployments require configuring S3-compatible cloud object storage (e.g. Supabase Storage or AWS S3) to ensure redundancy, edge CDN delivery, and persistence across container restarts.
* **In-Process vs Distributed Queue**:
  * The current job queue uses MongoDB collection polling (`ProcessingJob`) with atomic leases and heartbeat recovery (`reapStaleJobLeases`).
  * While durable across web server restarts and worker crashes, high-scale multi-cluster deployments with thousands of concurrent scans should integrate an enterprise Redis / BullMQ worker backend.
